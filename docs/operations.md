# 風景写真コンシェルジュ 運用フロー

このドキュメントは、風景写真コンシェルジュ（LINE Bot）の**改善・修正を安全に回すための手順書**です。
不具合の報告から、確認・実装・公開・記録までを一つの決まった流れに乗せることで、抜け・属人化・公開事故を防ぎます。

> **読み方**: 各セクションは「**概要**（どなたでも読めます）」と「**手順**（技術担当者向け）」の二層になっています。
> 全体像だけ知りたい方は概要だけを、実際に作業する方は手順まで読んでください。

> **このドキュメントに秘匿情報は書きません。** 認証情報・APIキー・接続URL・出品者名簿などは、本書には一切記載せず、
> 「Firestore のコンソールで」のように参照にとどめます。本書は公開・共有される前提で書かれています。

---

## 0. 最初に — このアプリの大原則

すべての判断は、次の原則の範囲内で行います。機能追加よりこれらが優先されます。

**概要**

- **データの守り**: 全件を一覧化する「近道」は作らない。表示は常に上限内・近い順の代表のみ。
- **入賞作品への敬意**: 出品作品は敬意をもって扱う。非公開の作品は決して表示しない。
- **正直さと安全のバランス**: 能動的なおすすめでは無理のある提案をしない。一方、利用者が明示的に指定した検索には、実在する結果を正直に返す（必要なら注意書きを添える）。

**手順（技術担当者向け）**

- 非公開判定: `Published` が `N` で終わるレコードは検索・表示から除外する。
- カルーセルは上限内（最大件数）の代表のみ。距離の起点が無い場合の既定起点も仕様どおりに保つ。
- 「地域＋被写体」検索は最頻出の中核機能。**ここを壊す変更は出さない**（回帰確認を必須とする）。

## 1. 受付窓口 — 報告はどこから来るか

**概要**

不具合や違和感の報告は、新しい窓口を作らず、**LINE の既存フィードバックボタンを正式な受付経路**とします。
作品カルーセルに付く「👍 ちょうど良い／🤔 ピンとこない／📍 場所に違和感」がそれです。
このほか、関係者からの口頭・メッセージでの指摘も受付に含めます。

**手順（技術担当者向け）**

- 受け付けた内容は、まず**事案として 6.台帳に1行記録**してから着手する（思いつきで直接コードに入らない）。
- 報告には「どの入力で」「何が起きたか」を最低限そろえる。スクリーンショットがあれば添える。

---

## 2. 正本は Firestore — データ修正の鉄則

**概要**

データ（撮影地・作品情報・表記など）の**正本は Firestore**です。
手元の CSV を直接アップロードして上書きすることはしません。事故と取り違えのもとになります。

**手順（技術担当者向け）**

データを修正するときは、次のいずれかの手順を踏みます。

1. Firestore のコンソール上で直接編集する、または
2. Firestore からエクスポート → 手元で修正 → 内容を確認のうえ取り込む。

検証用にデータを手元へ取り出す場合も、それは**読み取り専用の検証目的**に限り、そこから本番へ流すことはしません。

---

## 3. 運用フローの背骨（毎回この順序）

**概要**

どんな事案も、原則として次の順序で進めます。これが「背骨」です。
重さは事案の段階（4.severity）で変えますが、**順序は変えません**。

```
受付 → 確認 → 方針判断 → 実装 → 検証 → デプロイ → 公開確認 → 記録 →（必要なら）告知
```

**手順（技術担当者向け）**

| 工程 | やること |
|------|----------|
| 受付 | 報告を受け、台帳に起票（1.2） |
| 確認 | 再現する。正本データ（Firestore）の該当箇所を特定する |
| 方針判断 | 修正する／注意書きを添える／仕様として据え置く、を決める。大きな変更・文面はオーナーと相談 |
| 実装 | コードまたはデータを修正。小さく刻む（1事案＝1つのまとまり） |
| 検証 | コンパイル（構文確認）＋オフライン検証。最頻出の「地域＋被写体」の回帰確認を含める |
| デプロイ | GitHub へ反映 → Render が公開ビルド |
| 公開確認 | **実機（LINE）で確認**。手元の最新版と公開版が一致しているかをまず疑う |
| 記録 | 台帳に結果（判断・対応・日付）を追記 |
| 告知 | 利用者・関係者に影響がある場合のみ周知 |

> **検証の注意**: 開発用サンドボックスからは Firestore・画像・地図解決に到達できません。
> ロジックはオフライン（代理データや関数単体）で確かめ、データに依存する最終確認は実機で行います。

---

## 4. 事案の段階（severity）— 重さの使い分け

**概要**

すべてを同じ重さで回すと、軽い修正にまで全工程がかかって回らなくなります。
そこで段階を3つに分け、軽い事案は背骨の一部を省けるようにします。**順序は省きません、深さを変えます。**

**手順（技術担当者向け）**

| 段階 | 例 | 省略可 | 必須 |
|------|----|--------|------|
| **軽微** | 誤字、言い回しの調整 | 告知 | 受付・記録・実機での見た目確認 |
| **中** | 表示ロジックの変更（例: 注意書きの追加、日付解釈の拡張） | — | オフライン検証＋実機確認＋記録 |
| **重** | データの守りに関わる／非公開情報の漏れ／誤誘導による安全懸念 | — | 据え置き判断も含め記録必須。必要に応じ告知。慎重に複数回検証 |

判断に迷うときは、**一段重い扱い**にします。

---

## 5. 守ってはいけない一線（安全配慮）

**概要**

利用者を、無理のある場所や危険な状況に誘導しないよう配慮します。
たとえば冬期に閉山する山を、何も添えずに「撮り頃」として勧めることはしません。

**手順（技術担当者向け）**

- 参考スポット（おすすめ）は、そのスポットの開放月の外では出さない。
- 一方、利用者が明示的にそのスポットを検索した場合は、実在する作品を正直に出しつつ、**軽い注意書き**を添える。
- 新たに注意が必要なスポットが見つかったら、スポット定義に「閉山注記（`closed_note`）」を1行足す（→ 6.台帳に記録）。これが本書のいう「都度対応」です。

---

## 6. 台帳 — 事案の記録

**概要**

事案ごとに「いつ・何が・どう判断し・どう対応したか」を1行で残します。
過去の判断が見えることで、似た事案が来たときに一貫した対応ができます。

**手順（技術担当者向け）**

各事案を次の最小形式で本書末尾（または別ファイル）に追記します。

```
[日付] 段階 | 事案（どの入力で何が起きたか） | 判断 | 対応 | 確認方法
```

GitHub のコミット履歴も「いつ・誰が・なぜ変えたか」の記録として台帳を補完します。

---

## 7. このマニュアル自体の運用

**概要**

本書の更新も、軽微な事案として同じ背骨に乗せます。完璧な手順書を先に書くのではなく、
**最小で始め、実際の事案を1〜2件通して、回りにくい工程だけ足す／削る**方針です。

**手順（技術担当者向け）**

- 当面、**閲覧専用・更新はオーナー一人**。スタッフは読むだけ。改善要望は受付窓口（1）経由で受ける。
- 置き場所はリポジトリ内 `docs/operations.md`。秘匿情報は載せない（参照にとどめる）。

## 付録A. 記録の1件目 — 「上高地」冬期表示の対応（2026-06-11）

本書の運用を最初に通した実例です。今後の事案の書き方の見本にもなります。

**何が起きたか（概要）**

12月の上高地は閉山期で、装備のある登山者しか入れません。にもかかわらず、
「12月 長野」等の検索で、参考スポットとして上高地が提案されてしまうことがありました。
原因は、日付「12月」がうまく解釈されず、季節が今（6月）として扱われていたことでした。

**確認・原因（技術）**

- 日付解釈が「◯月」「上旬／中旬／下旬」に未対応で、月指定が効かず当日扱いになっていた。
- 参考スポットは開放月（上高地は4〜11月）の外では出さない仕組みがあったが、上記により月が正しく渡っていなかった。

**対応（技術）**

1. 時期の解釈を共通化し、「◯月」「上中下旬」「全角数字」を読めるよう拡張（季節は月単位で解決）。
2. 見出しの時期表現を、解釈結果から生成する単一の出所に統一。
3. スポット定義に「閉山注記」を持たせ、**開放月の外で、かつ利用者がそのスポットを指定（または結果に含まれる）とき**にだけ、
   カルーセル末尾へ軽い注意書きを添える対応を追加。
4. 入力のゆれ（スペースの有無、全角数字）でも結果が割れないことを確認。

**判断**

- 能動的なおすすめでは閉山スポットを出さない。
- 利用者が明示検索したときは、実在する冬の作品を正直に出しつつ、注意書きを添える（＝この一線を 5 に明文化）。

**確認方法**

- オフライン: 時期解釈・注意書き判定を関数単位で検証。
- 実機: 「12月 上高地」「12月上高地」（詰め）で、見出しが「12月に」、冬の作品が出て、末尾に注意書きが付き、
  参考スポットには上高地が出ないこと。「6月 上高地」では注意書きが付かないこと。

**台帳行**

```
[2026-06-11] 中 | 「12月 長野/上高地」で閉山期の上高地が提案される | 能動おすすめは出さない/明示検索は注意書き付きで正直に | 時期解釈の拡張＋閉山注記の追加 | オフライン＋実機(12月/6月の上高地)
```
